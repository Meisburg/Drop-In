**A note on `--resume`.** The lane was first started under a 30-minute wrapper
that would have killed it mid-run with no output. It was stopped at ~24 minutes
and `--resume <session-id>` was attempted; `ocr` **refused**: *"resume session …

review is not resumable — budget the whole run up front, or lose it.

## Verdicts

A machine-lane finding is a claim like any other. Every one below was checked
against the tree; two did not survive contact.

### CONFIRMED — a real defect, and it is a v29-2 regression

**`PlaceDetailsPage.tsx:263-283` (`high`, `bug`).** The going-line read sat
**inside the posts effect's `try`**, whose shared `catch` runs `setPosts([])`.
`listPingsForPosts` throws on a query error, so a failed *decorative* read
rendered **"Nothing planned yet."** for a place whose drop-ins had loaded fine —
a decorative read emptying the primary content, which is the exact lie-class
v29-2 exists to remove. `PlacePage.tsx` had already isolated the read in its own
effect with a catch that only resets pings state; **v29-2 missed this surface.**
The docblock it left behind reasoned correctly about `null` vs `{}` and never
noticed the `catch` below it also cleared the feed.

**FIXED.** The read moved into its own effect, the shape `PlacePage` uses.

### CONFIRMED — the same class, on all three card surfaces

**`ProfileView.tsx:318`, `PlacePage.tsx:243`, `PlaceDetailsPage.tsx:274`**
(`medium` + 2 `low`, `bug`). None reset the map before a new read, and
`goingPingsLoaded` at the render site **is literally `goingPingsByPostId !== null`**
(`PlacePage.tsx:723`, `PlaceDetailsPage.tsx:717`, `ProfileView.tsx:1041,1059`).
So a map describing a *previous* posts set stayed "loaded" for a new one, and
cards transiently asserted **"No one's going yet"** for posts whose pings had
never been read. Reachable where a route element is reused: a push deep link to
another place's `/place/:id/details` reuses `<PlaceDetailsPage/>`.

`FeedPage.tsx` sets the precedent (`setPingsByPostId(null)` before the read).

**FIXED** on all three, one reset each.

### CONFIRMED — the lane predicted a CI failure that nothing had ever run

**`e2e/time-presets.e2e.ts:81` (`low`, `test`).** The small-hours test pinned the
instant `2026-10-05T02:00:00-07:00` (= `09:00Z`) via `page.clock.setFixedTime`,
while the form computes its default slot in the **browser's** timezone and
`playwright.config.ts` sets no `timezoneId`. The lane argued the note therefore
never renders on a UTC runner.

**It was first recorded here as UNVERIFIED, and then it was settled by
experiment.** CI had never executed the test — the 2026-10-04 nightly checked out
`580eb82`, the V29 *base*, an hour *after* v29-5 landed — so CI could not decide
it. Running the spec directly did:

```
TZ=UTC npx playwright test e2e/time-presets.e2e.ts --reporter=line
→ 1 failed   [chromium] › e2e/time-presets.e2e.ts:80:1 › a small-hours start …
   at e2e/time-presets.e2e.ts:86  (expect(note).toBeVisible())
→ 2 passed
```

**The lane was right: the test failed deterministically on a UTC runner.** It had
never bitten only because nothing UTC had ever run it.

**FIXED — timezone-independently.** The fixture now pins an instant whose *local*
hour is 02:00 (`const smallHours = new Date(); smallHours.setHours(2, 0, 0, 0)`),
which preserves the test's meaning — a parent posting in the middle of the night
— on every runner, and keeps this process's timezone aligned with the browser's,
which the same file's day/slot assertions depend on. (Pinning only the browser via
`test.use({ timezoneId })` was rejected: it would desync the Node-side
expectations the other two tests compute.)

**Proved both ways:** `TZ=UTC` → **3 passed**; local `PDT` → **3 passed**.

### ACCEPTED, THEN FIXED (2026-10-04, same session)

Every one of these was verified against the code before the edit, then closed:

- **`scripts/mobile-audit.mjs` (`medium`, `bug`) — FIXED.** The vertical-containment
  check compared `rect.bottom` (VIEWPORT-relative, from
  `getBoundingClientRect()`) against `doc.scrollHeight` (DOCUMENT-level), so it
  was only correct while `window.scrollY === 0`. It now compares
  `rect.bottom + window.scrollY`. Latent when found — nothing scrolls before that
  `evaluate` today — but a later autofocused field on `/login` would have made a
  genuinely clipped control read as contained and **silently disarmed the check.**
- **`scripts/mobile-audit.mjs` — `/reset-password` ADDED to `FITS_ONE_SCREEN`
  and `ROUTES`.** Verified first: `ResetPasswordPage.tsx:61` renders the identical
  one-screen container as `/login`, so it made the same claim while its fold was
  unmeasured. Now measured — **it passes all 7 viewports in both light and dark**,
  so the gap was real but no defect was hiding in it.
- **`scripts/mobile-audit.mjs` — the below-the-fold loop now skips
  `display: inline`**, matching the tap-target loop's own rule ("inline links
  inside a sentence are running text, not controls").
- **`src/App.tsx:457` — the inverted conditional FLIPPED.** Removing the header
  sign-out left `session !== null ? null : <Link/>`; it now leads with the
  rendered element like every other conditional in the file.
- **`src/pages/FeedPage.tsx:1181`** — the `V27 slice 4` comment said "dismissing
  clears the state", which is exactly the behaviour v29-3 removed; corrected.

Verified after: `node scripts/mobile-audit.mjs` → **"All mobile checks passed."**
(7 viewports × light/dark × 4 routes), and `npm run verify` EXIT=0.
- **Four comments that contradicted shipped behaviour — CORRECTED** (commit
  `83e39a2`). The `push-subscribe.e2e.ts` header and the `PushOptInPrompt.tsx:29`
  docblock both still said **three** trigger points while v29-1 removed the signup
  arm and the spec's own test asserts its absence; the same spec's detail-page
  baseline still claimed "the signup point was answered above"; `push.ts`
  attributed `parseOfferedTriggers`' filter to `PUSH_PROMPT_TRIGGERS` when the
  filter is `isPushPromptTrigger` (the constant is the list it filters); and
  `FeedPage.tsx:1181` described exactly the banner bug v29-3 fixed.
