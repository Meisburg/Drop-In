# `ocr` review — the V29 range (2026-10-04)

The third review lane, run at last. `task-state.md`'s v29-11 entry recorded
**"`ocr` LANE UNAVAILABLE — not installed on this box"** and the batch closed
without it. That was a **false negative**: `ocr` is installed
(`open-code-review v1.12.11`) and configured against the local `ninfer` 5090. A
lane that lives only in a pointer table is a lane that quietly stops running; this
one ran.

**A note on `--resume`.** The lane was first started under a 30-minute wrapper
that would have killed it mid-run with no output. It was stopped at ~24 minutes
and `--resume <session-id>` was attempted; `ocr` **refused**: *"resume session …
was interrupted before it closed, so it never recorded a run manifest and its
input identity cannot be verified; start a new review instead."* So an interrupted
review is not resumable — budget the whole run up front, or lose it.

## Verdicts

A machine-lane finding is a claim like any other. Every one below was checked
against the tree; two did not survive contact.

### CONFIRMED — a real defect, and it is a v29-2 regression

**`PlaceDetailsPage.tsx:263-283` (`high`, `bug`).** The going-line read sat
**inside the posts effect's `try`**, whose shared `catch` runs `setPosts([])`.
`listPingsForPosts` throws on a query error, so a failed *decorative* read
rendered **"Nothing planned yet."** for a place whose drop-ins had loaded fine —
a decorative read emptying the primary content, which is the exact lie-class
v29-2 exists to remove. `PlacePage.tsx` had already isolated the read in its own
effect with a catch that only resets pings state; **v29-2 missed this surface.**
The docblock it left behind reasoned correctly about `null` vs `{}` and never
noticed the `catch` below it also cleared the feed.

**FIXED.** The read moved into its own effect, the shape `PlacePage` uses.

### CONFIRMED — the same class, on all three card surfaces

**`ProfileView.tsx:318`, `PlacePage.tsx:243`, `PlaceDetailsPage.tsx:274`**
(`medium` + 2 `low`, `bug`). None reset the map before a new read, and
`goingPingsLoaded` at the render site **is literally `goingPingsByPostId !== null`**
(`PlacePage.tsx:723`, `PlaceDetailsPage.tsx:717`, `ProfileView.tsx:1041,1059`).
So a map describing a *previous* posts set stayed "loaded" for a new one, and
cards transiently asserted **"No one's going yet"** for posts whose pings had
never been read. Reachable where a route element is reused: a push deep link to
another place's `/place/:id/details` reuses `<PlaceDetailsPage/>`.

`FeedPage.tsx` sets the precedent (`setPingsByPostId(null)` before the read).

**FIXED** on all three, one reset each.

### REFUTED

- **`e2e/zip-radius.e2e.ts` (`low`, `documentation`)** claimed a cross-reference
  named a helper that does not exist, and that the real helper is
  `patchMarkerLocation(zip, radiusMiles)`. **`patchMarkerRadius` exists** —
  defined at `e2e/zip-radius.e2e.ts:42` and called at `:173`, `:191`, `:204`.
  The lane invented a missing symbol. *A reviewer's citations need adjudication as
  much as its reasoning* — the same failure fr-1's audit had, from the other lane.
- **`DropInCard.tsx` / `PlaydateFormFields.tsx` (`low`, `style`)** asserted "the
  project rules disallow" nested ternaries. **No such rule is written** —
  `grep -rniE "nested ternary" docs/agents/code-structure.md AGENTS.md
  .opencodereview/rule.json` returns nothing, and `.oxlintrc.json` enables only
  `react/rules-of-hooks` and `react/only-export-components`. The refactor is a
  style preference, not a rule violation. (The *second* half of the
  `PlaydateFormFields` finding — that `smallHoursStartNote()` is evaluated twice
  per render — is a fair minor nit, accepted.)

### UNVERIFIED — and the lane was right to ask

**`e2e/time-presets.e2e.ts:81` (`low`, `test`).** The small-hours test pins the
instant `2026-10-05T02:00:00-07:00` (= `09:00Z`) via `page.clock.setFixedTime`,
while the form computes its default slot in the **browser's** timezone and
`playwright.config.ts` sets no `timezoneId`. The lane argues the note therefore
never renders on a UTC runner, failing deterministically there.

**This was checked and could NOT be settled either way.** The scheduled live lane
runs on a UTC runner, but the 2026-10-04 nightly checked out **`580eb82` — the
V29 *base* commit**, an hour *after* v29-5 landed. So CI has never executed this
test, and both "it passes on UTC" and "it fails on UTC" are unsupported. **Read it,
do not quote it: the test is unverified outside US timezones.**

## What this cost and what it bought

files, four stale-contract comments, and two fabricated/overstated findings. **The
lane earned its keep and it is not authoritative** — both halves of that are the
reason it stays in the rotation.
